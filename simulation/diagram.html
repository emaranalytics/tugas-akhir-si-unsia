📌 Cara Kerja Baseline

Pada pendekatan baseline, AI Agent meneruskan seluruh katalog tools ke dalam context window LLM tanpa seleksi apapun. LLM harus membaca dan mempertimbangkan semua tool definition sebelum dapat memilih satu tool yang sesuai dengan permintaan pengguna.

Tidak ada komponen penyaringan antara katalog tools dan LLM — setiap tool definition dikirim sebagai bagian dari prompt, lengkap dengan nama, deskripsi, dan skema parameter.

📊 Metrik Eksperimen

S1 (30 tools): 2.426 token
S2 (100 tools): 7.985 token
S3 (300 tools): 23.893 token
Akurasi S1: 68.8%
Akurasi S2: 71.4%
Akurasi S3: 71.4%

🔢 Masalah Utama: Pertumbuhan O(N)

1
Token bertumbuh linier
Setiap tool baru yang ditambahkan ke katalog langsung menambah ~80 token per panggilan LLM. Dari 30→100→300 tools, token naik dari 2.426→7.985→23.893.
2
Context Rot
LLM yang menerima konteks sangat panjang mengalami degradasi performa — informasi relevan yang berada di tengah konteks sering diabaikan (Liu et al., 2024 — "Lost in the Middle").
3
Biaya tidak terkendali
Biaya inferensi (API cost) tumbuh proporsional dengan jumlah tools. Untuk zerlo.id yang akan berkembang ke 1.000+ tools, baseline tidak layak secara ekonomis.

📌 Cara Kerja Tool Registry

Tool Registry adalah lapisan penyaring (filtering layer) yang berdiri di antara AI Agent dan LLM. Setiap tool dalam katalog didaftarkan dengan metadata terstruktur (ToolMeta). Ketika query masuk, registry memfilter katalog menggunakan 4 tahap sebelum meneruskan subset tools ke LLM.

Karena filtering bersifat deterministik dan berbasis in-memory Python dict, overhead latensi sangat kecil (<1ms) — tidak ada model ML atau database eksternal yang dibutuhkan.

🏗️ Skema ToolMeta

@dataclass class ToolMeta: tool_id: str # "inventory_check_stock" module: str # "inventory" op_type: str # "read" | "write" | "admin" keywords: list[str] # ["stok", "cek", "bahan baku"] role: str # "manager" | "cashier" | "admin" tier: str # "free" | "pro" | "premium" tokens: int # estimasi token definition ~80

🔄 4 Tahap Filter Pipeline

1
🔑 Ekstraksi Kata Kunci
Registry mengekstrak token-token penting dari query pengguna (tokenisasi sederhana + stopword removal). Hasil: daftar kata kunci yang akan dicocokkan.
2
🗂️ Pencocokan Modul
Kata kunci dicocokkan dengan field module dan keywords[] setiap tool. Tool dari modul yang tidak relevan langsung dieliminasi.
3
👤 Filter Role & Tier
Tool yang membutuhkan role atau tier lebih tinggi dari pengguna saat ini disembunyikan. Contoh: kasir tidak melihat tools administrasi sistem.
4
💰 Budget Cap
Tools diurutkan berdasarkan skor relevansi keyword. Maksimal 15 tools teratas yang diteruskan ke LLM — memastikan context window tetap kecil dan konstan.

📌 Cara Kerja Tool RAG

Tool RAG (Retrieval-Augmented Generation untuk tools) menggunakan representasi semantik berbasis embedding vector untuk menemukan tools yang paling relevan dengan query. Berbeda dengan registry yang mengandalkan metadata eksplisit, RAG memahami makna semantik — "bahan makanan" dapat terhubung ke "inventory" meskipun kata tersebut tidak ada dalam metadata tool.

Sistem bekerja dalam dua fase: offline (indexing semua tool descriptions ke vector DB) dan online (embedding query + nearest neighbor search per panggilan).

🔄 Alur Kerja Detail

1
Offline: Indexing Tool Catalog
Setiap tool description diubah menjadi embedding vector menggunakan model seperti text-embedding-004. Vektor disimpan di Vector DB (Pinecone, Chroma, Qdrant, dll).
2
Online: Embed Query
Query pengguna diubah menjadi embedding vector menggunakan model yang sama. Ini menambah latensi 50–200ms per panggilan dibanding registry.
3
Cosine Similarity Search
Vector DB mencari tools dengan vektor terdekat (cosine similarity terbesar) ke vektor query. Hasilnya adalah top-k tools paling "semantically similar".
4
Top-k ke LLM
Hanya k tools (biasanya 10–20) yang diteruskan ke LLM. Token yang digunakan mirip dengan registry (~950 token untuk S1).

⚖️ Kelebihan vs Kekurangan

✓
Memahami Makna Semantik
Dapat menghubungkan "pesan bahan" dengan "purchase order" meskipun kata kunci tidak exact match — cocok untuk query bahasa alami yang beragam.
✓
Skalabel untuk Ribuan Tools
Approximate nearest neighbor search berjalan O(log N) atau bahkan O(1) dengan HNSW index — efisien untuk katalog sangat besar tanpa struktur modul.
✗
Infrastruktur Kompleks
Membutuhkan: embedding model (hosted atau local), vector database, pipeline sinkronisasi saat katalog berubah. Overhead operasional signifikan.
✗
Latensi Tambahan
Setiap query membutuhkan embedding computation (50–200ms) + vector search. Dibandingkan registry <1ms, RAG menambah latensi yang terasa pada sistem real-time.
✗
Gagal untuk Tools Semantically Similar
Untuk query "Buat purchase order ke supplier tepung", RAG mengembalikan supplier_list_vendors (skor 0.76) hampir sama dengan supplier_create_po (0.88) — LLM bingung karena semantik mirip.

⚠️ Vector Database (Pinecone / Chroma / Qdrant)
⚠️ Embedding Model (hosted API atau local)
⚠️ Sync pipeline — re-embed saat catalog berubah

🏆 Mengapa Tool Registry adalah Pilihan Tepat untuk zerlo.id Saat Ini

🗂️
Metadata sudah tersedia secara alami. zerlo.id memiliki 38 modul terstruktur, sistem RBAC (role-based access control), dan tier subscription — semua metadata yang dibutuhkan Tool Registry sudah ada tanpa konfigurasi tambahan.
⚡
Zero infrastructure overhead. Tidak butuh vector DB atau embedding model — filter berjalan in-memory Python <1ms. Dapat langsung diintegrasikan ke codebase FastAPI + Pydantic AI yang ada.
📊
Terbukti secara statistik. Wilcoxon p<0.0001, Cohen's d≥11 — penghematan 63–95% token bukan kebetulan. Akurasi meningkat +6.3pp di S1 dan S3.
📈
Skalabilitas O(1) terbukti. Saat katalog berkembang dari 30→100→300 tools, token Registry tetap ~1.240 — bukan tumbuh linier seperti baseline. zerlo.id dapat scale ke ratusan modul tanpa degradasi performa.
🔮
Tool RAG sebagai natural next step. Saat zerlo.id berkembang ke ribuan tools atau menambah modul yang tidak memiliki struktur modul yang jelas, Tool RAG menjadi pilihan yang tepat — dan Tool Registry sudah menyiapkan metadata yang akan berguna sebagai filter tahap pertama dalam two-stage hybrid approach.
